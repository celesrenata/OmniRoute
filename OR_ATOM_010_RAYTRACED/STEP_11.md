# STEP 11: opt-in GPU / atom detail view

Base commit: `0c3d063b9` (plus the Step 11 commit that carries this file). Branch `feat/atomic-raytraced-renderer`. Not deployed, nothing pushed.
Environment: macOS, Apple M5 Max, headed Chrome via Playwright (real GPU), dev server from this worktree on :20199, golden DEMO topology (`/dev/atomic-bench?atoms=20`).

## What it is

The viewer focuses an atom (label click), the tooltip offers "Open detail view", and the camera flies in (low, near eye-level idea5-style hero framing, revision 2) while a DOM panel shows that atom's real telemetry. Escape / "Back to topology" restores the previous framing. The default view never changes: no detail code runs unless the viewer opts in.

## Honesty rules (directives 7 and 30)

- Values come from the descriptor; null device measurements read "no data", never 0.
- Active/Queued job panels appear only when `activeJobs`/`queuedJobs` are non-null (a real 0 is shown). Failed appears only from real `request-failed` events in the lifecycle pool for that provider within 60 s. GPU atoms have no provider id, so failures are never attributed to them. No value, no panel.
- Model to nucleon mapping uses only observed model ids and the scene's own deterministic nucleus allocator, with a basis label (live in-flight, call-log window, fleet residency). No model observed gives "neutral two-tone", nothing guessed.
- Activity wording reuses the tier text ("idle, no measured activity", "recent activity Nm ago"), so decorative vitality is never presented as live work.

## Camera (revision 2, directive 34.1)

Correction: the first Step 11 build claimed a "low three-quarter angle" but settled on a high-angle view with the atom at ~1/3 of the frame height. That claim is withdrawn.
The detail view now flies to a LOW, near eye-level shot (`detailFlight.ts`): distance, elevation and azimuth are interpolated in spherical coordinates to 214 units from the atom (just outside OrbitControls' 200 minimum), elevation 0.10 rad above the atom's horizontal plane, a 0.55 rad yaw sweep, and a telephoto field of view eased from 50 to 24 degrees (the orbit minimum distance is frozen, so the telephoto is what makes the atom fill the frame). The atom now spans about 52 to 55 % of the frame height on its pad, the board recedes to a visible horizon and the walls/room show behind it. DOF stays viewer-based (directive 32); neighbours are dimmed by the existing focus treatment. After the flight a slow bounded yaw sway (+/-0.2 rad, 38 s period, `driftYawRate`) keeps the shot alive; it stops when the viewer grabs the camera and is off in reduced motion. Esc / Back / Reset restore the exact prior framing (verified live, below).
Container clamp: the soft clamp re-applied its own output each frame, so any pose below about 254 units above the floor limit was pushed back up (it fought the low shot: the camera ended at y=251 instead of 69). While the detail view is open `clampRelax.detail` shrinks the band to 40 and the clearance to 30 (`containerBounds.ts`, `ContainerCameraClamp.tsx`, `AtomicScene.tsx::DetailFlight`). The camera still never reaches a wall, floor or ceiling (unit-tested). The default view never sets the flag.
Files changed for the camera: `detailFlight.ts`, `AtomicScene.tsx` (DetailFlight only), `containerBounds.ts`, `ContainerCameraClamp.tsx`. Not touched: `layout.ts`, `cameraFit.ts`, `SceneOrbitControls.tsx`, `AtomicLabels.tsx`, `AtomicControls.tsx`, the 2D renderer, telemetry semantics, routing.

## Labels and activity wording (directive 34.2, 34.3)

- The focused atom's label is hidden while the detail view is open and the other labels fade to 40 % (`overlays/detailLabelCss.ts`, a scoped stylesheet; the frozen label file is untouched).
- One shared vocabulary (`overlays/activityVocabulary.ts`): the label chip prints `visualState.state`; the tooltip and panel print `"<chip word> . <tier text>"`. GPU/runtime atoms used to be hard-wired to chip "idle" while their tier could be 3; their visual state is now derived from the tier (`deviceVisualStateInput`), so chip, tooltip and panel agree (live: GPU atom chip "active" / "Activity: active . active (live or measured work)"; real provider chip "last" / "last . recent activity < 1m ago"; hub chip "idle" / "idle . idle, no measured activity"). Atom visual state is read only by the label chip and tooltip, never by rendering.
